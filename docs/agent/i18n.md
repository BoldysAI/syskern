# docs/agent/i18n.md — Multilingue & traduction (CDC §10)

> Domaine i18n : contenus produit multilingues (FR/EN/ES), service DeepL + cache,
> couverture catalogue, traduction bulk, résolution de la langue des offres.
> Règles transverses → `/AGENTS.md`. Clients HTTP externes → `integrations.md`.
> Async → `celery-task.md`. Réf code : `apps/i18n/`, `apps/offers/services/translation.py`,
> `apps/offers/services/offer_i18n.py`, `frontend/src/components/MultilingualField.tsx`.

Langue source = **FR** (fait foi, CDC §10.2). EN/ES dérivées (saisie manuelle ou DeepL).
Contenus multilingues = JSONB `{"fr","en","es"}` (`Product.description_marketing`/
`description_technical`, `AttributeRegistry.label`).

## Langue d'interface (story 7.1)

Distincte du DeepL. Préférence du compte, sinon langue du déploiement.

```text
langue affichée =
  Profile.locale          si fr ou en
  sinon DEFAULT_UI_LOCALE variable d'environnement (une par serveur)
  sinon "fr"
```

- `Profile.locale` optionnel. Formulaire admin Utilisateurs : Français, English, ou vide (« langue du déploiement »). Story 7.8 : le menu du compte (barre latérale) écrit le même champ via `PATCH /api/auth/locale`. Le choix est relu à la connexion suivante par `resolve_ui_locale`.
- `resolve_ui_locale` (`apps/accounts/ui_locale.py`) est le seul calcul. Login et `GET /api/auth/session` renvoient `locale` et `display_language`.
- Français = catalogue source. Clé absente en anglais → le français de cette clé seule.
- Front : `frontend/src/lib/i18n.ts` assemble les catalogues de `frontend/src/lib/i18n/catalogs/`. Les écrans appellent `useUiTranslate()` (`frontend/src/lib/use-ui-translate.ts`). Story 7.5 : chaque clé d'écran a une entrée anglaise (navigation, catalogue, fiche produit, fournisseurs, simulations, comparaisons, offres, bibliothèque, paramètres, utilisateurs, quarantaine). Story 7.6 : les erreurs, validations et libellés renvoyés par l'API ont leur anglais dans `EN` (`apps/accounts/ui_locale.py`). `_proof.only_fr` reste sans anglais : c'est la preuve du repli. Les contenus produit (DeepL) ne passent pas par ce catalogue.
- En-têtes Excel / Gamma d'une offre : indexés par la **langue d'offre** (`fr`/`en`/`es`) dans `excel.py` et `project_generator.py`, pas par la langue d'interface. Les exports tableur catalogue, simulation et rapport de lignes rejetées suivent la langue d'interface de celui qui télécharge (story 7.7).
- `<html lang>` part de `fr`, puis `DocumentLanguage` le remplace par `fr-FR` ou `en-GB` (`uiDateLocale`) dès que la session est connue. Le masque des champs date suit cette valeur.
- Story 7.9 : dates, nombres et montants **affichés** suivent `display_language` (`formatUiDate`, `formatUiDateTime`, `formatUiNumber` dans `frontend/src/lib/i18n.ts` ; `fmtEur` / `fmtNum` / `fmtPrice` prennent la même locale). Anglais = `en-GB` (virgule de milliers, point décimal). Le symbole ou le code devise reste après le montant (`1,234.56 €`). Ça ne change pas la lecture d'un fichier entrant : l'import PO, les cellules Excel et le parsing §B.4 gardent les séparateurs du document, pas la préférence de celui qui consulte l'écran. `parseLocaleNum` ne relit que des chaînes que l'écran vient d'afficher (écarts de comparaison).
- La bulle native d'un champ obligatoire (« Veuillez renseigner ce champ ») suit la langue du navigateur, pas `lang`. `DocumentLanguage` la remplace par `common.validity.*` dans la langue du compte.
- `DEFAULT_UI_LOCALE=fr` sur le serveur France. Pas de modèle Entité.
- Ajouter une langue = un catalogue + une valeur acceptée. Pas de ressources chinoises.

## Messages API (story 7.2)

Erreurs HTTP visibles (`ValidationError`, `PermissionDenied`, `detail`, `Http404`) : `translate(key, resolve_ui_locale(user))` (`translate_request` depuis une requête DRF). Phrase source dans `FR`. Story 7.6 : chaque clé a son anglais dans `EN`, sauf `_proof.only_fr`, qui retombe sur le français pour prouver le repli par libellé.

Un worker Celery n'a pas de requête. Une tâche lancée par un utilisateur reçoit sa langue au `delay()` (`resolve_request_locale(request)`) et traduit avec : message d'échec renvoyé par `GET /api/tasks/{id}/` (`refresh_pamp_task`, `translate_product_task`, `bulk_translate_products_task`, `recalculate_task`, `export_simulation_task`, génération d'offre tarif/projet, régénération), `generation_error` stocké sur l'offre, motifs de l'import PO. Paramètre `locale: str | None = None` : sans langue (tâche planifiée comme `reap_stuck_generations`, appel direct), repli sur `resolve_ui_locale(None)`, la langue du déploiement — jamais `fr` en dur.

Échecs de services externes : l'utilisateur lit une phrase du catalogue, le texte brut reste dans les logs du worker.
- `generation_error` : `offers.generation_timeout` ou `offers.generation_failed` (clé API, corps HTTP Gamma/OpenAI jamais stockés sur l'offre).
- Offre tarif sans taux EUR → devise cible : le `ValueError` du moteur (`missing_fx_rate_message`, français) est rattrapé à la frontière de la tâche et relevé en `offers.fx_missing`. Le moteur n'est pas modifié.
- Recalcul en mode dégradé (Odoo injoignable) : `odoo_refresh_error` = `simulations.odoo_unreachable` ; la note de l'historique garde le détail Odoo (`simulations.odoo_refresh_note`).
- DeepL (`translate_product_task`, `bulk_translate_products_task`) : `_translation_failure` mappe quota / indisponible / texte trop long / autre vers `products.translation_*`.

`test_ui_literals.py` refuse toute exception levée avec un texte littéral dans un `tasks.py`, sauf `odoo_sync/tasks.py` (déclenché par signal ou beat, aucun écran ne suit la tâche). Il ne voit que le texte écrit dans le `raise` : un `str(exc)` relayé ou une exception levée plus bas (client DeepL, moteur) passe. Ces cas sont traduits à la frontière de la tâche et ont leurs propres tests. Les diagnostics du moteur de pricing restent du payload de calcul, pas des erreurs HTTP.

Login non authentifié : erreurs (`auth.missing_credentials`, `auth.invalid_credentials`, `auth.rate_limited`) toujours dans la langue du déploiement. Prendre la langue du compte lié à l'e-mail révélerait que le compte existe.

Front hors React (`lib/api.ts`, fetchers SWR, `useAutosave`) : `getApiLocale()`, tenu à jour par `DocumentLanguage` via `setApiLocale(displayLanguage)`. `pollTask` et les replis `common.httpError` / `common.loadError` passent par là. Incoterms : `localizeIncotermLabel(label, code, displayLanguage)` et texte d'impact `simulator.incotermImpact.<CODE>`.

Les deux validations de `POST /api/translate` (`i18n.text_or_texts`, `i18n.langs_must_differ`) passent par le catalogue. Les échecs DeepL de cet endpoint synchrone (quota, service indisponible, clé absente) restent le texte porté par l'exception ; dans les tâches produit, ils passent par le catalogue (ci-dessus).

Hors catalogue d'interface : les libellés d'offre déjà indexés par la langue d'offre (`excel.py`, `project_generator.py`, y compris l'espagnol), diagnostics du moteur de pricing stockés sur la ligne, journaux Celery, commandes de management, rapports d'étapes `data_migration`.

## Filet ESLint (story 7.3)

`frontend/eslint-rules/no-literal-ui-string.mjs`, branchée en erreur dans `eslint.config.mjs` sur `src/**/*.{ts,tsx}` (hors `src/lib/i18n/**`). Une chaîne affichable qui n'est pas une clé de catalogue fait échouer `npm run lint`.

Est affichable : texte JSX, attributs `placeholder` / `title` / `alt` / `aria-*`, propriétés d'objet `label` / `title` / `description` / `placeholder` / `alt` / `message` / `subtitle` / `hint` / `heading` quand la valeur est une phrase, et les replis `||` / `??` du même genre. Le premier argument de `t()` / `translate()` n'est pas signalé.

Ne sont pas des libellés : clé `domaine.cle`, identifiant en minuscules (`viewer`, `draft`, `fr`), code court ISO (`EUR`, `SKU`, `EXW`) hors texte JSX, classe CSS, ponctuation seule (`—`, `…`). Le texte JSX « SKU » ou « Excel » reste un libellé : il passe par une clé dont la valeur française est ce mot.

Tests de la règle : `node --test eslint-rules/no-literal-ui-string.test.mjs` (API `Linter`, pas `RuleTester` — le parseur JSX de `RuleTester` ne remonte pas les erreurs).

Côté vues : `apps/core/tests/test_ui_literals.py` échoue si `views.py` ou `serializers.py` passe une chaîne littérale à `ValidationError`, `PermissionDenied` ou `Http404`. Le message passe par `translate` / `translate_request`.

## Exhaustivité des catalogues (story 7.4)

`apps/core/tests/test_catalog_coverage.py`, lancé par `pytest`. Pas de pipeline d'intégration continue dans le dépôt : c'est ce test qui bloque. Il échoue si une clé française n'a pas d'anglais non vide, côté écrans (`frontend/src/lib/i18n/catalogs/`) et côté API (`FR` / `EN` dans `ui_locale.py`). `_proof.only_fr` est la seule clé sans anglais. Les clés `exports.*` (en-têtes catalogue, simulation, rapport d'import) y sont. Les tables `fr`/`en`/`es` des offres restent dans `excel.py` et `project_generator.py` : elles suivent la langue d'offre, pas ce test.

## Parcours de recette (story 7.10)

`apps/core/tests/test_en_acceptance_path.py`, même gate `pytest`. Il rejoue le parcours catalogue → fiche → export catalogue → export simulation → offre tarif en anglais. Il échoue si une clé appelée par ces écrans ou ces vues n'a pas d'anglais (le libellé resterait le français source), ou si un libellé de structure déjà traduit apparaît en français dans les trois fichiers. Le nom produit stocké (`Câble cat7`) reste dans la cellule : ce n'est pas un libellé.

Le conteneur `backend` ne monte que `backend/` : le contrôle des écrans (catalogues frontend) y est sauté. Rejeu complet devant le Client :

```bash
docker compose run --rm -v "$PWD/frontend:/frontend:ro" backend pytest apps/core/tests/test_en_acceptance_path.py
```

## Documents générés (story 7.7)

Libellés de structure seulement : titres d'onglet, en-têtes de colonnes, mentions fixes (oui/non, statuts, conditions, note de change). Les désignations, noms, gammes et descriptions produit restent le texte stocké (DeepL). Le diagnostic moteur dans la feuille breakdown reste le payload enregistré ; seul le préfixe `ERREUR` / `ERROR` est un libellé.

- Offre tarif Excel et devis Gamma : langue de l'offre (`offer.language`, `fr`/`en`/`es`).
- Export catalogue (`products/exports.py`), export simulation (`simulations/exports.py`), rapport des lignes rejetées à l'import PO (`suppliers/tasks.py`) : langue d'interface de la requête, passée au moment du `delay` Celery (`locale=`). Un worker n'a pas de requête : si l'appelant ne la fournit pas, l'export suit la langue du déploiement (`resolve_ui_locale(None)`).

## Service de traduction (CDC §10.4)

- **Client** : `apps/offers/services/translation.py::DeepLClient` (dans `offers`, pas
  `app/clients/` — cf. `decisions.md`). `translate()` + `translate_batch()`.
  `preserve_formatting=1` sur chaque appel ; `formality=more` **uniquement** si la langue
  cible le supporte (ES oui, EN non — sinon DeepL répond 400). Après DeepL, la casse du
  texte source est réalignée (`apply_source_casing`) pour conserver ALL CAPS / Title Case
  anglais lors d'un EN→FR (sinon `formality=more` normalise en typographie française).
  Erreurs typées :
  timeout 10 s), `TranslationInputError` (>5000 car.), `TranslationError` (auth/config).
  401/403 → log + email (`TRANSLATION_AUTH_ALERT_RECIPIENTS`).
- **Auth & hôte DeepL** (gotchas dev, cf. `decisions.md`) :
  - Auth = en-tête `Authorization: DeepL-Auth-Key <clé>` — **plus** de `auth_key` dans le body
    (legacy → HTTP 403 trompeur « authentication failure »).
  - Hôte auto : clé Free (suffixe `:fx`) → `https://api-free.deepl.com/v2` ; clé Pro →
    `https://api.deepl.com/v2`. Surcharge optionnelle `DEEPL_API_URL` dans `.env`.
  - Clé absente → `503` « Service de traduction non configuré… » (pas de 500).
- **Variables d'env** (`backend/.env`) : `DEEPL_API_KEY` (requis pour traduire),
  `DEEPL_API_URL` (optionnel), `TRANSLATION_CACHE_TTL_DAYS` (défaut 90),
  `TRANSLATION_AUTH_ALERT_RECIPIENTS`. Après changement de clé → redémarrer le backend ;
  traduction bulk → redémarrer Celery aussi.
- **Cache** : app **`apps/i18n`** (label `app_i18n`), modèle `TranslationCache`
  (`db_table="translation_cache"`) : `source_text_hash` UNIQUE (sha256 `src|tgt|text`),
  `expires_at`, `hit_count`. TTL `TRANSLATION_CACHE_TTL_DAYS` (défaut 90).
  Service read-through : `apps.i18n.services.translate_cached(text, src, tgt) -> (texte, from_cache)`
  et `translate_many_cached(...)` (batch, regroupe les miss). **Écart CDC §10.4.3** (table
  dédiée vs JSONB) tracé dans `decisions.md` ; le JSONB produit reste la source des fiches.
- **Endpoint** : `POST /api/translate` (`apps/i18n/views.TranslateView`) — **synchrone**
  (écart règle §4, cf. `decisions.md`). Body `{text | texts[], source_lang, target_lang}`
  (batch cap 50). Réponse `{translated_text, from_cache}` ou `{translations:[…]}`.
  `456`→402, `503`→503 (quota/indispo/auth/config), trop long→400. Le front appelle **toujours**
  cet endpoint, jamais DeepL directement. `MultilingualField` affiche le `detail` API en cas d'erreur.
- **Purge** : Beat `i18n.purge_translation_cache` (03:30 UTC, migration `app_i18n/0002`).

## Frontend multilingue

- **`components/MultilingualField.tsx`** (réutilisable) : 3 onglets FR/EN/ES, input **ou**
  textarea (`kind`), point d'état par onglet (rempli=vert / vide=ambre + `sr-only`),
  bouton « Traduire depuis FR » (EN/ES) → `translateText()` (`/api/translate`, remplit
  l'onglet, éditable). `mode="read"|"edit"`, `requiredSource` marque FR d'un `*`.
  Props : `{ value:{fr,en,es}, onChange, mode, kind, label, requiredSource, rows }`.
  Utilisé par : `catalog/[sku]/_tabs/DescriptionsEditor` (descriptions), `settings/attributes/
  _components/AttributeFormModal` (label). **Notes fournisseur = hors scope** (texte simple).
- API (`lib/api.ts`) : `translateText`, `startBulkTranslate`, `getTaskStatus`,
  `checkOfferCoverage`, type `I18nCoverage`.

## Couverture multilingue (CDC §10.7.3)

- Backend : `Product.i18n_coverage` (`{languages, percent, complete}`) exposé sur
  `ProductListSerializer` + détail. Filtres catalogue :
  - `?i18n_incomplete=true` — au moins une des 3 langues manquante ;
  - `?lang_fr_in=true` / `lang_fr_out=true` (idem `en`, `es`) — avec / sans contenu dans
    descriptions marketing ou technique (`ProductFilter._lang_covered_q`).
- Front : colonne « Langues » activable via la modale colonnes catalogue
  (`CatalogColumnsDialog` / `catalog-column-storage.ts`, largeur compacte ~76px) ;
  filtres sidebar : « Au moins une langue manquante » + par langue « Avec contenu » /
  « Sans contenu » (mutuellement exclusifs par langue). **Aucun libellé « i18n »** visible
  utilisateur. Chips/compteur via `active-filters.ts`.

## Traduction bulk (CDC §10.3.2)

- Backend : `products.bulk_translate_products_task` (bind, `update_state("PROGRESS",
  {current,total})`) — ne remplit que les langues **vides** (n'écrase jamais), abort clair
  sur quota/indispo. Endpoint `POST /api/products/bulk-translate/` (202 + task_id) ;
  serializer `BulkTranslateSerializer` (`ids, source_lang, target_langs, content_fields`).
- Front : `catalog/_components/BulkTranslateDialog` ouvert depuis la `selectionBar` du
  catalogue (`canEdit`) — choix langues/champs, progress bar (poll `/api/tasks/{id}/`), récap.

## Résolution langue offre (CDC §10.5)

- **Tarif par client** : `GenerateTariffOffersSerializer.language_per_client` (défaut false).
  `true` → chaque offre = `client.preferred_language or language or "fr"` (résolu dans
  `generate_tariff_offers_task`). Wizard tarif : toggle « Langue par client (automatique) ».
- **Projet** : wizard pré-remplit la langue avec `client.preferred_language` (surchargeable).
- **Fallback** (`services/offer_i18n.resolve_product_description`) : langue cible sinon FR
  (`fallback_used`) ; les replis sont **loggés** à la génération (`_log_language_fallbacks`).
- **Pré-génération** : `POST /api/simulations/{id}/offer-coverage-check/` (body `{language}`
  ou `{client_ids, language_per_client}`) → `{languages, products[], product_ids[]}`.
  UI : `components/OfferCoverageWarning` (dans les 2 wizards) — warning + « Traduire
  automatiquement » (bulk translate des `product_ids` puis re-check).

## Checklist i18n

- [ ] Nouveau contenu multilingue → JSONB `{fr,en,es}`, FR requis ; UI via `MultilingualField`
- [ ] Appel DeepL → jamais dans une vue directe : `/api/translate` (court) ou tâche Celery (bulk)
- [ ] Cache : passer par `apps.i18n.services.translate_cached` (jamais `DeepLClient` nu hors offres)
- [ ] Couverture : `Product.i18n_coverage` + filtre `i18n_incomplete` si nouveau champ traduisible
- [ ] Offre dans une langue cible → résoudre via `offer_i18n` + logguer les fallbacks
- [ ] Message API visible → clé `FR` + `translate` / `translate_request` (pas d'anglais inventé) ; migrations committées si modèle touché
- [ ] Dev local : clé Free `:fx` + endpoint `api-free` auto ; auth header (pas body) — cf. gotchas §10.4
